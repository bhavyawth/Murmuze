# PROJECT OVERVIEW
═══════════════════════════════════════════════════════════════════════════════

PROJECT NAME: Murmuze Enhanced - Real-Time Messaging & Communication Platform

WHAT IT DOES:
Murmuze is a feature-rich real-time chat application that combines instant
messaging with peer-to-peer video/voice calls, gamification elements, and
advanced messaging capabilities. It's designed for engaging, persistent
social communication with built-in engagement incentives.

PROBLEM SOLVED:
- Replaces fragmented communication tools (separate chat + video apps)
- Adds engagement through gamification (XP, levels, achievements, streaks)
- Provides rich messaging features (voice messages, polls, time capsules)
- Includes ephemeral messaging (ghost mode - messages disappear after 60s)
- Enables real-time interactions with read receipts, typing indicators, reactions

TARGET USERS:
- Friend groups wanting a centralized chat platform
- Communities seeking engagement-driven communication
- Users wanting integrated calling without switching apps
- Teams/individuals tracking communication metrics and engagement

KEY HIGHLIGHTS:
✓ WebRTC peer-to-peer video/audio calls with low latency
✓ Gamification system (XP, levels, achievements, daily streaks)
✓ Rich message types (text, images, voice, polls, time capsules)
✓ Real-time features (typing indicators, read receipts, reactions)
✓ Friend system with request/accept workflow
✓ Chat analytics (message stats, activity heatmap, top words, call history)
✓ Ephemeral messaging (ghost mode)
✓ Responsive UI with 32 themes
✓ Cloudinary integration for media storage
✓ JWT authentication with secure cookies

# MAIN FEATURES
═══════════════════════════════════════════════════════════════════════════════

1. REAL-TIME MESSAGING
───────────────────────
- Text messages with instant delivery via WebSocket
- Image sharing with Cloudinary cloud storage
- Voice messages (record & send audio from browser)
- Message reactions (8 quick emoji reactions)
- Reply to messages (quote threading)
- Delete messages (mark as deleted, not permanently removed)
- Read receipts (sender sees when message is read)
- Typing indicators (see when someone is typing)

How it works:
  Frontend sends message → Backend uploads media to Cloudinary
  → Creates message record in MongoDB → Broadcasts via Socket.io
  → Receiver sees notification & unread count


2. VIDEO & VOICE CALLS
──────────────────────
- Real WebRTC peer-to-peer calls (no server media relay)
- Video calls with camera toggle on/off
- Voice-only calls with audio streaming
- Mute microphone during calls
- Call history with duration tracking
- Automatic call rejection if user offline

How it works:
  Caller initiates call → Socket.io signals offer (SDP)
  → Receiver accepts with answer (SDP)
  → ICE candidates exchanged for NAT traversal
  → Direct media stream established between peers
  → Call log saved to MongoDB with duration


3. GAMIFICATION SYSTEM
──────────────────────
- XP System: 5 XP earned per message sent
- Levels: Every 100 XP = +1 level
- Daily Streaks: Track consecutive daily messages
- Achievements: 9 unlockable badges including:
  • First Message, 100+ Messages
  • Night Owl (message between 12am-5am)
  • Image/Voice/Poll Achievements
  • 7-day & 30-day streak badges

How it works:
  User sends message → Backend awards XP
  → Calculates new level → Checks achievement conditions
  → Updates user record → Sends achievement event to frontend
  → Leaderboard sorts users by XP


4. POLLS & TIME CAPSULES
─────────────────────────
POLLS:
- Create poll with 2-5 options
- Live vote percentages
- Real-time update when someone votes
- Each user votes once per poll

TIME CAPSULES:
- Schedule message delivery for future date/time
- Message stored with "scheduled" status
- Server checks every 60 seconds for deliverable messages
- Automatic delivery when scheduled time arrives
- Uses background worker process

How it works:
  Poll created → Stored in Message.poll field
  → Real-time updates broadcast via Socket.io
  
  Time capsule scheduled → Marked with scheduledFor + isDelivered:false
  → Background worker finds due messages
  → Marks as delivered → Emits 'newMessage' to recipient


5. GHOST MODE (EPHEMERAL MESSAGES)
──────────────────────────────────
- Toggle "Ghost Mode" in message input
- Next message sent disappears after 60 seconds
- Message stored with expiresAt timestamp
- Server worker deletes after timeout
- Removed from UI when expired

How it works:
  Message sent with disappearAfter: 60 (seconds)
  → Backend sets expiresAt = now + 60s
  → Background job finds expired messages every 10 seconds
  → Emits 'messageExpired' socket event to both users
  → Removes message from database


6. FRIEND SYSTEM & CONTACTS
────────────────────────────
- Send/receive friend requests
- Accept or decline requests
- Only chat with accepted friends
- Search users by name/email
- View friend profiles with stats

How it works:
  User A searches → Finds User B
  → Clicks "Add Friend" → Request stored in B's pendingRequests
  → B sees request notification → Accepts/declines
  → Friendship added to both users' friends arrays


7. CHAT ANALYTICS & STATISTICS
───────────────────────────────
- Total message count (mine vs theirs)
- Hourly message distribution (bar chart)
- Top 10 most-used words
- Image/audio count
- Activity heatmap (daily message count for 365 days)
- Call history (missed/answered/rejected calls with duration)
- League ranking (Gold/Silver/Bronze based on XP)

# APPLICATION FLOW
═══════════════════════════════════════════════════════════════════════════════

AUTHENTICATION & INITIALIZATION:
1. User loads app
2. Frontend checks for JWT cookie via /auth/check
3. If valid → load authUser state, connect WebSocket, show home
4. If invalid → redirect to login/signup

LOGIN FLOW:
1. User enters email/password
2. Frontend POST to /auth/login
3. Backend verifies credentials with bcrypt
4. If valid → JWT created & stored in httpOnly cookie
5. Socket.io connects with userId as query param
6. Backend maps userId → socketId for real-time messaging

CHAT INITIALIZATION:
1. Select friend from sidebar
2. Frontend GET /messages/{friendId} → fetches all messages
3. Frontend subscribes to socket events:
   - newMessage
   - messageDeleted
   - messageExpired
   - reactionUpdate
   - messagesRead
   - userTyping/userStoppedTyping
4. Unread count cleared for selected friend

MESSAGE SENDING:
1. User types & clicks send
2. If image → upload to Cloudinary first
3. POST to /messages/{friendId} with message data
4. Backend saves to MongoDB
5. Awards XP to sender
6. Checks for achievement unlocks
7. Updates activity log & streak
8. Broadcasts 'newMessage' via Socket.io
9. Receiver sees notification (if online)

CALL FLOW:
1. Caller clicks "Video" or "Voice" button
2. Frontend requests camera/microphone permissions
3. Local stream captured via getUserMedia
4. WebRTC offer (SDP) created & sent via Socket.io
5. Receiver sees incoming call modal
6. Receiver accepts → creates answer (SDP)
7. Both peers exchange ICE candidates
8. Direct media connection established
9. Call duration tracked in frontend
10. Either party hangs up → call logged to MongoDB with duration

MESSAGE EXPIRATION FLOW (Ghost Mode):
1. Message sent with disappearAfter: 60 seconds
2. Backend sets expiresAt = now + 60s
3. Message stored normally but tracked for expiration
4. Server-side worker checks every 10 seconds
5. Found expired messages → emit 'messageExpired' to both users
6. Frontend receives event → removes message from state
7. Message deleted from database

  _id: ObjectId
  senderId: UserId (ref: User)
  recieverId: UserId (ref: User)

  text: String
  image: String (Cloudinary URL)

  gif: String (Cloudinary URL)

# AUTHENTICATION & SECURITY
═══════════════════════════════════════════════════════════════════════════════

AUTHENTICATION FLOW:

SIGNUP:
1. User submits email, fullName, password
2. Backend validates required fields
3. Checks if email already exists
4. Hashes password with bcryptjs (10 salt rounds)
5. Creates new User document in MongoDB
6. Generates JWT token via generateToken()
7. JWT stored in httpOnly cookie (secure + sameSite)
8. Returns user data (no password) to frontend

LOGIN:
1. User submits email, password
2. Backend finds user by email
3. Compares password with bcrypt.compare()
4. If match → generateToken() + set JWT cookie
5. Returns user data
6. Frontend stores authUser in Zustand state

LOGOUT:
1. Frontend POST to /logout (requires auth)
2. Backend clears JWT cookie
3. Frontend clears authUser state
4. Redirects to login page

TOKEN HANDLING:
- generateToken() creates JWT with userId + exp
- JWT payload: { userId, iat, exp }
- Default expiry: 7 days
- Stored in httpOnly cookie (prevents XSS)
- Sent automatically in all requests (cookie middleware)

PROTECTED ROUTES:
- Middleware protectRoute validates JWT
- Extracts userId from token
- Attaches to req.user
- All message/call/friend endpoints require auth

SECURITY PRACTICES:
✓ Passwords hashed (bcryptjs 10 rounds - not salted in DB)
✓ JWT in httpOnly cookies (XSS protection)
✓ CORS restricted to CLIENT_URL only
✓ Secure flag on cookies in production
✓ SameSite=None for cross-site; Lax otherwise
✓ Input validation on all endpoints
✓ Soft deletes prevent data loss
✓ User can only access own data
✓ File uploads limited to 20MB
✓ Media stored in Cloudinary (not on server)

POTENTIAL VULNERABILITIES:
- No rate limiting on auth endpoints (needs implementation)
- No input sanitization (XSS risk on poll text, etc.)
- Weak password requirements (6 chars minimum)
- No CSRF protection (frontend should use SameSite)
- Message search not paginated (full DB query)

# CHALLENGES & DESIGN DECISIONS
═══════════════════════════════════════════════════════════════════════════════

1. REAL-TIME MESSAGE DELIVERY

Challenge:
  How to reliably deliver messages when users disconnect?
  
Decision: Two-layer approach
  ✓ Socket.io room-based delivery (instant if connected)
  ✓ Database persistence + unread badge (offline users)
  ✓ Marked 'isRead' when user opens chat
  
Why: Balances performance (no DB hit if online) with reliability
(messages persist if offline)


2. WEBRTC PEER CONNECTION ESTABLISHMENT

Challenge:
  Firewall/NAT traversal for direct peer-to-peer calls
  
Decision: ICE candidate exchange via Socket.io
  ✓ STUN servers for NAT traversal (Google public STUN)
  ✓ Queue ICE candidates until remote description ready
  ✓ Flush queue after setting remote SDP
  
Why: Standard WebRTC pattern ensures compatibility
(works through most firewalls + corporate networks)


3. GHOST MESSAGE EXPIRATION

Challenge:
  Messages must auto-delete after 60s; how to handle offline users?
  
Decision: Server-side + client-side dual cleanup
  ✓ Server checks every 10 seconds for expired messages
  ✓ Emits 'messageExpired' socket event to both users
  ✓ Client-side fallback: checks every 5s locally
  ✓ Database record deleted server-side
  
Why: Ensures deletion even if client disconnects + offline
users see deletion when they reconnect


4. GAMIFICATION SCORING

Challenge:
  How to prevent spam/gaming the XP system?
  
Decision: Simple flat rate (5 XP/message, no diminishing returns)
  ✓ No rate limiting (could be added)
  ✓ Every message counts equally
  ✓ Achievements require specific conditions (not just XP)
  
Why: Trade-off between engagement + simplicity
(could add rate-limiting for production)


5. STATE MANAGEMENT: ZUSTAND VS REDUX

Challenge:
  Manage complex state (auth, chat, calls, friends, theme)
  
Decision: Zustand (lightweight + simple)
  ✓ Less boilerplate than Redux
  ✓ Direct state mutations (no actions needed)
  ✓ Devtools support available
  ✓ Middleware for effects/subscriptions
  
Why: Project doesn't need Redux complexity + Zustand is faster
to develop with + smaller bundle


6. MEDIA UPLOAD: CLOUDINARY VS LOCAL STORAGE

Challenge:
  Store images/voice/GIFs; how to handle scaling?
  
Decision: Cloudinary cloud storage
  ✓ No server storage needed

# LIKELY VIVA/INTERVIEW QUESTIONS & ANSWERS
═══════════════════════════════════════════════════════════════════════════════

Q1: What is the tech stack and why did you choose it?

A: The frontend uses React 19 with Vite for fast development and bundling.
State management is Zustand—lightweight and simple compared to Redux. Styling
is Tailwind + DaisyUI. The backend is Express.js on Node.js for simplicity and
npm ecosystem. MongoDB for flexible document storage, Socket.io for WebSocket
real-time messaging, and Cloudinary for media storage to avoid server storage
limits.

Why these choices? React is industry-standard with large ecosystem. Zustand
avoids Redux boilerplate for a project of this scale. Express is minimal and
fast. Zustand, Express, and Node together create a lightweight, performant
stack. Cloudinary outsources image handling complexity.


Q2: How do you handle real-time messaging?

A: Socket.io provides persistent WebSocket connections. When a user sends a
message, the frontend POSTs to /messages/{userId}, the backend saves to
MongoDB, broadcasts 'newMessage' via Socket.io to the recipient, and updates
are pushed to the UI in real-time. Typing indicators and read receipts work
similarly—socket events without database hits for performance.


Q3: How does WebRTC calling work? Why peer-to-peer?

A: WebRTC establishes direct media streams between browsers. When caller clicks
"Video", we capture local media (camera + mic), create a WebRTC offer (SDP),
send via Socket.io signaling to the receiver. Receiver creates an answer and
exchanges ICE candidates with the caller. Once connected, media flows
peer-to-peer—no server relay needed.

Why P2P? Lower latency (direct connection), reduced server costs (no media
relay), better privacy (media encrypted between peers), scalability (no server
bottleneck for calls).


Q4: How do you prevent XP/gamification gaming/spam?

A: Currently, the system is simple: 5 XP per message, no rate limiting. This
is intentional to encourage engagement early. For production, I'd add rate
limiting (1 message/second per user), require friend relationships to chat
(prevents bot spam), and possibly diminishing returns for identical messages.
Achievements have specific conditions (e.g., night owl requires 12am-5am), so
can't spam farm them.


Q5: How do you handle message persistence for offline users?

A: Messages are persisted to MongoDB immediately. When a recipient comes online,
they fetch unread messages via GET /messages/{userId} and the unread badge
clears when they open the chat. Read receipts are tracked via isRead field and
readAt timestamp. This balances instant delivery (when online) with reliability
(when offline).


Q6: What is the ghost message feature and how does it work?

A: Ghost mode sends a message that disappears after 60 seconds. When sent, the
message includes expiresAt = now + 60s. A background worker runs every 10
seconds, finds messages where expiresAt <= now, emits a 'messageExpired' socket
event to both users (who remove it from UI), and deletes from database. 

If a user is offline during expiration, they receive the event when reconnecting.
Client-side fallback checks every 5 seconds for expired messages locally.


Q7: How does authentication work?

A: On signup/login, the backend validates credentials and generates a JWT
stored in an httpOnly cookie. The cookie is sent automatically on all requests.
The protectRoute middleware verifies the JWT, extracts the userId, and attaches
it to req.user. This way, all protected endpoints know who the user is.

Why httpOnly cookies? Prevents XSS (JavaScript can't access cookies).
Why JWT? Stateless (no session store needed), scalable, works with microservices.


Q8: How do you scale this to millions of users?

A: 
- Horizontal scaling: Multiple Node instances behind a load balancer
- Redis: Replace in-memory Socket.io state + session store
- Database: Sharding by userId, read replicas for analytics queries
- Elasticsearch: For fast message search
- Message queue: Bull/RabbitMQ for background jobs (instead of timers)
- CDN: Already using Vercel for frontend + Cloudinary for media
- Microservices: Separate auth, messaging, calls, analytics if needed


Q9: What are the main performance optimizations?

A: 
- Backend: Database indexes on (senderId, recieverId, createdAt) for fast
  queries. Lazy population to avoid loading unnecessary fields.
- Frontend: Vite code splitting, lazy component loading, debounced typing
  indicator, Zustand for minimal re-renders.
- Real-time: Socket.io over WebSockets (vs HTTP polling), reduced bandwidth.
- Media: Cloudinary auto-optimization + CDN distribution.

Current bottleneck: Message search (full table scan). Solution: Full-text
indexes + pagination.


Q10: How do you handle concurrent users/calls?

A: Socket.io can handle thousands of concurrent connections with built-in
auto-reconnection. For calls, ICE candidates are queued until remote
description is set, ensuring reliable connection. Call metadata (callId,
callerId, receiverId, startedAt) stored in memory. For production, use Redis
adapter to share state across multiple servers.


Q11: Why MongoDB over SQL (PostgreSQL)?

A: MongoDB's document model fits the schema well:
- Flexible fields per message (text, image, audio, gif, poll, etc.)
- No complex joins needed (denormalized messages)
- Embedded arrays (reactions, poll votes) are natural
- Time-series data (activityLog as Map) is native
- Easier horizontal scaling (sharding)

SQL would work too, but require more joins and complex queries. MongoDB is
faster to develop with for this use case.


Q12: What security issues exist and how would you fix them?

A: 
- No rate limiting: Add express-rate-limit to auth endpoints
- No input sanitization: Use DOMPurify for XSS protection
- Weak password requirements: Enforce 12+ chars, special chars
- No CSRF protection: SameSite cookie already set
- SQL injection N/A: Using Mongoose (ORM), not raw queries
- Message search pagination missing: Add skip/limit

Production fixes: Implement all above + HTTPS (already done), OAuth for
social login, 2FA, audit logging, IP blocking.


Q13: How do you handle message reactions/polls?

A: Reactions are embedded in the Message.reactions array: 
[{ userId, emoji }, ...]. When a user reacts, backend adds to array, emits
'reactionUpdate' via Socket.io. UI updates live.

Polls: Message.poll stores { question, options: [{ text, votes: [userIds] }] }.
When user votes, backend adds their ID to the option's votes array, emits
'pollUpdate'. If they re-vote, old vote is replaced.


Q14: What happens if a user goes offline during a call?

A: When a user closes the tab/disconnects WiFi:
- Socket.io detects disconnect
- Backend emits 'callEnded' to other peer
- Other peer's UI closes the call modal
- If both disconnect, call is logged as "ended" with duration

If only one disconnects mid-call, the other needs to manually hang up or wait
for timeout. This is a limitation of WebRTC (no server notification on
browser crash).


Q15: How do you track activity and generate the heatmap?

A: Every message updates user.activityLog (Map), keyed by date string
(YYYY-MM-DD). Value = message count for that day. The activity heatmap
frontend component fetches this and renders a grid with color intensity.

Example: { "2025-06-01": 12, "2025-06-02": 0, "2025-06-03": 5 }

For 365-day heatmap: generate on demand from activityLog field (no DB query).
